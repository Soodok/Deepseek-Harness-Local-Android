# M9 性能与资源报告 · 无障碍记忆系统 v2

日期：2026-11-11 · 设备：emulator-5556（Android 11，x86_64，pt-BR）· APK 43.7 MB

## 1. 录制开销（A/B 对照，12+12 次同屏 /tap，取中位数）

| 组 | 中位数 | p25 | p75 |
| --- | --- | --- | --- |
| 录制 OFF | 68.7 ms | 55.0 | 87.2 |
| 录制 ON | 108.9 ms | 92.8 | 272.2 |
| **差值** | **+40.2 ms/动作** | — | — |

拆解：一次 `dumpScreenCompact` 实测 5 ms（`GET /screen` 同路径），写盘 <20 ms（`record slow` 日志阈值未触发），
其余是一次额外读屏 + flush 的固定成本。

- 相对本地闭环（1.7 s/步）＝ **+2.4%**，可接受。
- 相对模型逐步调 `/tap`（68 ms 基线）＝ **+59%**，偏高。
- **优化方向（未做）**：`/loop/run` 每步本来就有 dump，把它传进录制器可把 40 ms 压到 ~5 ms。
  这条是 M9 里唯一「已知可优化但本轮没做」的性能项，理由：loop 集成属于 M5 的后续重构，
  在没做端到端回归前不动它更安全。

## 2. 重放 vs 手打（同一 2 步任务，各 3 次）

| 方式 | 单次耗时 | 中位数 |
| --- | --- | --- |
| 重放 `/memory/run`（本地闭环，每步一次读屏 + settle） | 1.25 / 0.93 / 0.99 s | **0.99 s** |
| 手打（`/tap` + `/key`，含两次 HTTP 往返） | 0.79 / 1.76 / 1.55 s | **1.55 s** |

**重放比手打快 0.56 s**，但这不是主要收益 —— 两者都还走本地闭环。
真正的收益是**省掉一次云端规划往返**（实测 0.6–1.6 s/次，见 `docs/A11Y_MEMORY_DESIGN.md` §2），
以及失败重规划的往返。上面的对照**故意不含规划**，就是为了不把规划时间算进重放的功劳里。

## 3. 存储占用（真机实测）

| 项 | 实测 |
| --- | --- |
| `files/memory/`（1 条 2 步记忆） | 24 KB（目录含 v2 子目录） |
| 单条记忆 JSON | 1,621 B |
| `files/traces/`（4 条轨迹） | 48 KB |
| 单条轨迹 JSONL（2 步 / 8 步） | 1,744 B / 8,223 B |

上限推演：记忆 500 条 × ~2 KB ≈ **1 MB**；轨迹 200 个 × ~5 KB ≈ **1 MB**。合计 ≤2 MB，可忽略。
（容量与 TTL 由 `MemoryRetention.PER_PKG=50 / GLOBAL=500` 与 `TraceContract.TTL_MS=7天 / MAX_FILES=200` 保证。）

## 4. 检索延迟

| 后端 | 观测 |
| --- | --- |
| hash 降级（bge 不可用） | `POST /memory/v2/lookup` 单次 < 100 ms（10 条候选） |
| bge 嵌入（512 维，实测） | **中位 44 ms**（5 次：42 / 47 / 65 / 44 / 36 ms） |

bge 实测条件：emulator-5556（x86_64，CPU 推理）、`llama-cpp` 扩展 v0.9.0、
模型 `bge-small-zh-v1.5-q4_k_m.gguf`（15,448,256 B），10 条候选 + 1 次查询嵌入。
准确率同批实测见 `docs/reports/G4.md` §3（词面 10/10、语义 7/10）。

注意：查询嵌入是一次 512 维推理，条目向量在**入库时**算好落盘（`vectorDim=512`），
检索时不再逐条推理 —— 所以延迟与库大小基本无关，只随候选数线性增长。

## 5. 关闭录制时的开销

`recordEnabled=false` 时：`onActionBegin` 立即返回（不读屏）、`onActionDone` 立即返回（不读屏不写盘）、
`onBoundaryEnd` 只做 `pruneOld`（一次目录扫描，无文件时 <1 ms）。
A/B 的 OFF 组就是这条路径的实测：68.7 ms 与未接入前的 `/tap` 基线一致。
