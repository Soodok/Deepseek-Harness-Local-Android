# TIER_HASH：没有 bge 时 tier=high 到底能不能拿到

> 目的：`tier=high` 决定「记忆能不能自动重放」。它由三路加权决定
> （`0.6·cos + 0.3·fpJaccard + 0.1·anchor`，阈值 high≥0.85 / mid≥0.65，
> 见 `app/src/main/java/app/dsh/mobile/engine/MemoryIndex.kt:55-61`）。
> 在没有 llama.cpp 扩展、只能用 hash 引擎的设备上，「自动重放几乎不触发」是一个
> 未经验证的猜测。本文用实测数字把它钉死，给「要不要改分档策略」提供依据。
>
> 这是一把**量尺**，不是断言：程序只打印分数表，不做任何通过/失败判定。

## 跑法

```bash
bash scripts/measure-tier.sh
```

- `scripts/jvm/TierMeasure.kt`：构造 4 条同屏记忆（打开设置里的显示 / 声音 / 电池 / 存储页），
  `sceneFp` = 设置首页文本 + `pkg:com.android.settings`；锚点恒为 `Display`（模拟用户从设置首页出发）。
- 4 类意图 × 3 种屏幕指纹：
  - 意图：`exact`（一字不差）/ `word-order`（语序与语气词改写）/ `synonym`（跨词表语义改写）/ `unrelated`（无关任务）
  - 指纹：`1.0` 同屏 / `0.5` 半屏变化 / `0.0` 读不到屏
- 引擎：hash（`engine=hash`），即**没装 llama.cpp 扩展的用户所处的真实状态**。

## 结论

1. **「hash 引擎下 high 只有一字不差才拿得到」是错的。**
   `帮我把设置里的显示页打开` 的 cos 仍有 **0.79**，同屏 score **0.87 → high，会自动重放**。
   hash 引擎是字符 bigram，对语序调整、语气词增删不敏感——用户用词和录制时相近就能命中。

2. **bge 不可替代的场景只有一个：跨词表语义改写。**
   `调一下屏幕亮度` 对 `打开设置里的显示页` cos=**0.03**，即便屏幕完全一致（fp=1.0）也只有
   **0.42 → low**，绝不自动执行。这类命中只有真向量能救。

3. **安全边界是有效的。** 无关任务（`在微信里给妈妈发个红包`）在同屏下 cos=0.06 → score 0.44 → low；
   语义改写与无关任务的分差只有 0.02，说明 hash 引擎**分不出「像」和「不像」**，
   所以低分档不能放宽——放宽等于把无关任务放进自动执行。

4. **读不到屏时保守是对的。** fp=0.0 时一字不差也只有 0.70 → mid，不会自动重放。
   屏幕指纹是「这一步在当前界面还成立吗」的第二道校验，缺了它不该自动动手。

## 对决策的影响

- **保持现状（默认）**：hash 引擎已覆盖「用户复述同类任务」这个主场景，自动重放不是不可用，
  只是不跨词表。手动传 `id` 重放始终可用。
- **不要做「屏幕完全一致直通高档」**：fp=1.0 时无关任务已经 0.44，直通会把它抬进 high，
  等于用一个便利换掉整类安全边界。
- **提高 fp 权重的收益有限**：fp 从 1.0 掉到 0.5，exact 仍 0.88 high、word-order 掉到 0.75 mid；
  真正卡住命中的是 cos，不是 fp。
- **引导装 llama.cpp 扩展的真实增量**：只在跨词表语义改写（synonym 档）。要不要为此增加安装门槛，
  属于产品取舍，需用户拍板。
