## 3. 设计取舍

- **为什么只记成功的步**：失败尝试由 loop 自己重试（`onFail.retry`），写进轨迹只会让剪枝器和记忆都变脏。
- **为什么复用 verify 的 dump**：`verifyStep` 本来就要读屏判 `anyText`，把那一屏交给录制器等于
  录制开销 0；只有 `key back` 这类**无 verify** 的步才补一次 dump（实测 ~30-60ms）。
- **为什么白名单与重放器同源**：`MemoryReplay.dispatch` 只有 tap/tap_id/gesture/input/key/scroll/launch +
  noop + scroll_to + scroll_find 分支。`set_switch` / `repeat` / `pinch` / `swipe` 在 loop 里能用，
  但重放器不认 —— 这类轨迹入库就是「能召回、一跑就废」，必须在入库前拒掉。
- **为什么不给 swipe 反推方向**：`swipe.dir=up`（手指上移）≡ `scroll.direction=down`（看下面的内容），
  语义相反；自动换算是猜，猜错就是点错页。要滚动请用 `scroll`。

## 5. 未覆盖

- `input` / `scroll` / `scroll_find` 步的录制只有静态映射，没有真机跑过（本次 loop 用例不含这三类）。
- 一次 loop 中途失败时，已成功的前几步会留在轨迹里（符合预期），但「失败步被丢弃」没有专门断言。
- 录制开销只做了单次观感对比（1391ms vs 1482ms，且步数不同），没有按 `docs/reports/PERF_MEMORY.md`
  的口径做 5 次中位数。
